VERDICT: VULNERABILITY DETECTED (BEARER TOKEN LOGOUT REVOCATION BYPASS)
EXPLOITABLE: True
DETAILS:
1. Cookie-based Logout: SECURE. When logging out with the access_token cookie, the server sets UserSession.revoked_at in PostgreSQL and clears cookies. Subsequent token replay attempts return HTTP 401 'Session revoked or not found'.
2. Bearer-based Logout: VULNERABLE (SEC-AUTH-02). get_current_user accepts both Cookies and 'Authorization: Bearer <token>', but /api/v1/auth/logout line 292 only extracts `request.cookies.get(ACCESS_COOKIE)`. When an API or mobile client sends `Authorization: Bearer <token>` to /logout without cookies, `token` is None. The server skips revocation, sets revoked_at to None, and returns 204 No Content. The JWT remains fully valid (HTTP 200) until natural expiration (30 minutes).

TEST: SEC-CSRF-01 - CSRF & Cross-Origin Request Forgery Surface
VERDICT: MITIGATED BY SAMESITE=LAX & CORS PREFLIGHT; LACKS EXPLICIT ANTI-CSRF TOKENS
EXPLOITABLE: False
DETAILS:
1. State-mutating POST endpoints do NOT implement or require an explicit anti-CSRF token header (e.g., X-CSRF-Token or Double Submit Cookie).
2. However, primary CSRF protection is provided by the SameSite=Lax cookie attribute, which prevents modern browsers from sending the access_token cookie on cross-site subrequests (fetch, XHR, image tags, iframe).
3. Furthermore, all mutating endpoints consume JSON payloads (application/json), which triggers a mandatory browser CORS preflight (OPTIONS). The CORSMiddleware whitelist rejects untrusted origins (returns 400 or omits Access-Control-Allow-Origin), so standard cross-origin fetch is blocked before execution.
4. FINDING / DEFENSE-IN-DEPTH DEFICIT: Server-side handlers do NOT check or enforce the `Origin` or `Sec-Fetch-Site` header directly. If a non-preflight request with cookies reached the server (e.g., in legacy user agents or via sub-domain takeover within the same site), the server executes the mutation because no CSRF token is verified.
